# 租户管理（第一阶段）

操作列提供停用/启用。状态保存在各租户 `tenant_profile.enabled`，新租户默认
启用；旧租户未包含该列时视为启用，首次修改状态时补充该列。停用保留业务
数据并清除公司登录会话，登录、后续 API、页面和 LINE 回调均拒绝访问，
定时调度跳过停用租户。重新启用后必须重新登录。原业务库仍需先接入租户管理。

入口：`/tenant-management/login/`；管理首页：`/tenant-management/`。

固定平台账号：`platform_admin`；初始密码：`MatchSys@2026`。
账号和密码哈希在 `credentials.py` 中维护，不使用数据库账号表。
部署前更换密码哈希，更改固定凭据会使已有平台会话失效。

平台使用独立的 `matchsys_platform_session` Cookie 和 Django 文件会话，
不使用公司业务数据库，也不赋予公司用户登录身份。退出时删除服务端会话。
文件会话默认使用系统临时目录；生产环境应配置受保护、可写的
`SESSION_FILE_PATH`，多实例部署需要共享该目录。使用 HTTPS 时启用
`SESSION_COOKIE_SECURE`。过期会话文件可通过 Django `clearsessions` 清理。

管理首页提供公司名、邮箱域名及操作列表，以及新建租户、重置管理员密码、
删除租户弹框。删除必须输入完整域名确认，删除对象是该租户整个数据库。

新建时从当前业务数据库复制表结构（保留约束），只复制菜单数据，初始化
管理员角色、员工、登录账号及公司配置；不复制原公司的客户或其他业务数据。
初始管理员账号为 `admin@域名`，密码遵循当前 MatchSys 的存储方式。
初始化失败会清理本次创建的新数据库。当前实现不复制视图、触发器和存储过程。

Schema 命名为 `matchsys_XXXX`，输入框只填写 `XXXX`，邮箱域名为 `XXXX.com`。
例如 `matchsul.com` 对应 `matchsys_matchsul`，统一使用小写，保留域名中的连字符。
旧命名的租户仍可列出、更新密码和删除；已有数据库不会自动改名。
超出 MySQL 64 字符数据库名限制时拒绝创建。各租户数据库中的 `tenant_profile`
记录公司名、域名及管理员 ID，不创建公共租户表。

原业务数据库以“现有业务库，待接入”显示，读取 `company-info`，不允许删除或
重置其管理员。新租户已接入业务登录及数据库路由；原业务库仍需单独迁移接入。

验证：6 项自动测试通过；使用临时 Schema 完成 MySQL 创建、列表、密码更新、
业务空表及删除验证，临时 Schema 已清理。
